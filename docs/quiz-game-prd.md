## 1. 개요

### 1.1 목적
브라우저에서 바로 실행되는 4지선다 상식 퀴즈 게임을 만든다. 사용자는 카테고리를 골라 문제를 풀고, 매 문항마다 정답 여부를 즉시 확인하며, 마지막에 점수와 순위를 기록한다.

### 1.2 배경
짧은 시간(3~5분) 안에 끝나는 가벼운 퀴즈 경험을 목표로 한다. 회원가입이나 서버 없이도 완결된 플레이가 가능해야 하며, 점수 기록을 통해 반복 플레이 동기를 만든다.

### 1.3 타깃 사용자
- 자투리 시간에 가볍게 퀴즈를 풀고 싶은 일반 사용자
- 자신의 이전 점수와 비교하며 반복 도전하는 사용자

## 2. 목표 및 성공 기준

| 목표 | 성공 기준 |
| --- | --- |
| 한 판을 끊김 없이 완주 | 카테고리 선택부터 결과 화면까지 이탈 없이 도달 |
| 즉각적인 피드백 | 선택 후 300ms 이내에 정답/오답 표시 |
| 반복 플레이 유도 | 결과 화면에서 "다시 하기" 진입률 확보 |
| 기록 보존 | 새로고침·브라우저 재실행 후에도 랭킹 유지 |

### 2.1 설계 원칙
**충분히 생각할 시간을 보장한다.** 상식 퀴즈의 순기능은 문제를 곱씹고 해설을 읽으며 알게 되는 데 있다. 속도를 점수로 보상하는 장치는 도입하지 않으며, 제한 시간은 경쟁 요소가 아니라 한 판의 길이를 예측 가능하게 만들기 위한 장치로만 둔다. 기능 추가 시 이 원칙과 충돌하는지 먼저 확인한다.

## 3. 범위

### 3.1 v1 포함
- 4지선다 객관식 퀴즈 진행
- 카테고리 4종: 한국사 / 과학 / 지리 / 일반상식
- 카테고리별 10문제, 총 40문제 문제 은행
- 정답/오답 즉시 피드백 + 해설 표시
- 점수 계산 및 결과 화면
- 랭킹(순위) 기록 및 조회
- 반응형 UI (모바일 우선)

### 3.2 v2 로드맵 (v1에서 대비하는 확장)
아래 두 가지는 v1 범위 밖이지만 도입이 확정된 방향이므로, v1 설계 단계에서 교체·확장 가능한 구조를 잡아둔다.

- **문제 은행 확장** — 카테고리당 10문제를 넘어 지속적으로 문제를 추가한다. → FR-1.2, FR-1.3
- **서버 기반 전체 사용자 랭킹** — Supabase 등 DB를 붙여 다른 사용자와 경쟁한다. → FR-6.8

### 3.3 v1 제외 (미정)
- 로그인 / 계정 시스템
- 문제 추가·수정 관리자 화면
- 멀티플레이 / 실시간 대결
- 문제 신고, 즐겨찾기, 오답 노트

## 4. 사용자 흐름

```
[홈]
  └─ 카테고리 선택 ──┬─ 단일 카테고리 (10문제)
                    └─ 전체 도전 (40문제)
         │
         ▼
[퀴즈 진행] ── 문제 표시 → 보기 선택 → 즉시 피드백(정답/오답 + 해설) → 다음 문제
         │                                                              │
         │◄─────────────────────── 마지막 문제까지 반복 ─────────────────┘
         ▼
[결과] ── 점수 / 정답 개수 / 소요 시간 / 오답 목록
         ├─ 닉네임 입력 → 랭킹 등록
         ├─ 다시 하기
         └─ 랭킹 보기
         │
         ▼
[랭킹] ── 모드·카테고리별 상위 기록 목록
```

## 5. 기능 요구사항

### FR-1. 문제 은행
| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| FR-1.1 | v1 출시 기준 카테고리 4종 각각 10문제, 총 40문제를 보유한다 | 필수 |
| FR-1.2 | 한 판의 출제 문항 수는 은행 크기와 분리된 상수로 관리한다 (v1: 카테고리당 10문항). 은행이 커져도 코드 수정 없이 문항 수가 유지된다 | 필수 |
| FR-1.3 | 은행의 문제 수가 출제 문항 수보다 많으면 무작위 표본을 추출한다 | 필수 |
| FR-1.4 | 직전 판에 출제된 문제는 다음 판 표본 추출에서 후순위로 밀어 중복 체감을 줄인다 | 권장 |
| FR-1.5 | 각 문제는 질문, 보기 4개, 정답 인덱스, 해설을 포함한다 | 필수 |
| FR-1.6 | 문제 데이터는 코드와 분리해 카테고리별 JSON 파일로 관리한다 (`data/history.json` 등) | 필수 |
| FR-1.7 | 문제 출제 순서와 보기 4개의 표시 순서를 매 판마다 섞는다 | 필수 |
| FR-1.8 | 문제 ID는 고유하며, 문제 추가 시 기존 ID를 재사용하지 않는다 | 필수 |
| FR-1.9 | 앱 시작 시 문제 데이터의 형식 오류(보기 개수 불일치, 정답 인덱스 범위 초과 등)를 검사하고, 불량 문제는 출제에서 제외한다 | 권장 |

> **확장 시 주의**: 은행이 커져 표본 추출이 실제로 동작하기 시작하면 판마다 문제 세트가 달라져, 랭킹의 동일 조건 비교가 깨진다. v1(은행 = 출제 수)에서는 문제가 없으나, 문제 추가 시점에 "고정 세트 챌린지 모드" 도입 여부를 다시 검토한다.

| FR-5.6 | 전체 모드에서는 카테고리별 정답 개수를 분리해 보여준다 | 권장 |
| FR-5.7 | 해당 모드·카테고리의 기존 최고 점수와 이번 점수를 비교해 표시한다 (예: 최고 80점 → 이번 90점, 신기록). 기존 기록이 없으면 첫 기록임을 안내한다 | 필수 |

### FR-6. 랭킹
| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| FR-6.1 | 결과 화면에서 닉네임(2~10자)을 입력해 기록을 등록한다 | 필수 |
| FR-6.2 | 랭킹은 모드·카테고리별로 분리해 관리한다 | 필수 |
| FR-6.3 | 정렬 기준은 점수 내림차순, 동점 시 기록 시각(`playedAt`) 오름차순이다. 즉 먼저 달성한 기록이 위로 온다. 소요 시간은 순위에 반영하지 않는다 (2.1 설계 원칙) | 필수 |
| FR-6.4 | 각 랭킹별 상위 10개를 저장·표시한다. 목록에 소요 시간은 표시하지 않으며, 결과 화면의 개인 지표로만 남긴다 | 필수 |
| FR-6.5 | 방금 등록한 기록은 목록에서 하이라이트한다 | 권장 |
| FR-6.6 | 랭킹 전체 초기화 기능을 제공한다 (확인 절차 필요) | 권장 |
| FR-6.7 | 기록은 브라우저 재실행 후에도 유지된다 | 필수 |
| FR-6.8 | 랭킹 저장·조회는 저장소 어댑터 인터페이스(`saveRecord` / `getRankings`)를 통해서만 호출한다. v1은 로컬 구현체를 사용하고, v2에서 서버 구현체로 교체할 때 게임 로직은 수정하지 않는다 | 필수 |
| FR-6.9 | 저장소 호출은 비동기(Promise)로 설계해, 동기식 로컬 구현에서 비동기 서버 구현으로 넘어갈 때 호출부가 바뀌지 않도록 한다 | 필수 |
| FR-6.10 | 랭킹 화면 상단에 현재 기록의 범위(이 브라우저에 저장된 내 기록)를 명시한다 | 필수 |
| FR-6.11 | 마지막에 입력한 닉네임을 기억해 다음 등록 시 기본값으로 채운다 | 권장 |
| FR-6.12 | 기록이 없는 초기 상태에서는 빈 랭킹임을 안내하고 첫 판을 유도하는 문구를 표시한다. 가상 기록은 심지 않는다 | 필수 |

## 6. 데이터 모델

### 6.1 문제 (Question)
```json
{
  "id": "history-001",
  "category": "history",
  "question": "훈민정음이 반포된 해는?",
  "choices": ["1443년", "1446년", "1450년", "1392년"],
  "answerIndex": 1,
  "explanation": "1443년에 창제되고 1446년에 반포되었습니다.",
  "difficulty": "easy",
  "tags": ["조선", "세종"]
}
```

`difficulty`와 `tags`는 v1에서 사용하지 않지만, 문제 은행이 커진 뒤 난이도별 출제·주제별 필터를 붙일 때 기존 문제를 일괄 수정하지 않도록 처음부터 스키마에 포함한다. (`difficulty`: `easy` / `normal` / `hard`)

카테고리 코드: `history`(한국사), `science`(과학), `geography`(지리), `general`(일반상식)

### 6.2 랭킹 기록 (ScoreRecord)
```json
{
  "id": "uuid",
  "nickname": "홍길동",
  "mode": "category",
  "category": "history",
  "score": 80,
  "correctCount": 8,
  "totalCount": 10,
  "durationMs": 96400,
  "playedAt": "2026-08-04T12:30:00+09:00"
}
```

`mode`는 `category` 또는 `all`. `mode`가 `all`이면 `category`는 `null`.

### 6.3 저장소 키
| 키 | 내용 |
| --- | --- |
| `quiz.rankings` | ScoreRecord 배열 |
| `quiz.settings` | 음소거 여부 등 사용자 설정 |
| `quiz.nickname` | 마지막으로 입력한 닉네임 |
| `quiz.recentQuestionIds` | 직전 판에 출제된 문제 ID 목록 (중복 회피용) |
| `quiz.schemaVersion` | 저장 데이터 스키마 버전. v2 마이그레이션 시 판단 기준 |

## 7. 화면 정의

| 화면 | 주요 구성 요소 |
| --- | --- |
| 홈 | 게임 타이틀, 카테고리 카드 4개(최고점 표시), 전체 도전 버튼, 랭킹 보기 버튼 |
| 퀴즈 | 진행률 바, 문제 번호, 질문, 보기 4개, 피드백 영역, 다음 버튼, 나가기 |
| 결과 | 점수, 정답률, 소요 시간, 최고 기록 대비 비교, 등급 메시지, 오답 리뷰, 닉네임 입력, 다시 하기 / 홈 / 랭킹 |
| 랭킹 | 모드·카테고리 탭, 상위 10개 목록(순위·닉네임·점수·날짜), 저장 범위 안내, 초기화 |

## 8. 비기능 요구사항

- **반응형**: 모바일 우선, 320px 폭까지 레이아웃이 깨지지 않을 것
- **성능**: 첫 화면 로딩 1초 이내, 문제 전환 지연 없음
- **오프라인**: 네트워크 없이도 전체 플레이 가능
- **접근성**: 보기 버튼 키보드 포커스 이동 가능, 정답/오답을 색상만으로 구분하지 않고 아이콘·텍스트 병행
- **데이터 무결성**: 저장된 랭킹 데이터가 손상된 경우 앱이 죽지 않고 빈 랭킹으로 복구

## 9. 기술 가정

- 프레임워크 없는 바닐라 JS + HTML + CSS 단일 페이지 구성
- 빌드 도구 없이 파일 그대로 서빙 가능한 구조를 유지한다. 배포는 GitHub Pages 등 정적 호스팅
- 상태는 메모리에서 관리하고, 랭킹·설정만 localStorage에 영속화
- 문제 데이터는 카테고리별 JSON으로 분리해 정적 로드
- 랭킹은 저장소 어댑터를 거쳐 접근하며, v1 구현체는 localStorage 기반
- 게임 로직(출제·채점·타이머)과 화면 렌더링을 분리해, v2에서 프레임워크 이전 시 로직을 재사용할 수 있게 한다

### 9.1 랭킹 저장소 범위 (중요)

v1 랭킹은 **각 방문자의 브라우저에만 저장된다.** 정적 호스팅에 올려 여러 사람이 접속하더라도 기록은 공유되지 않으며, 닉네임을 입력받아도 그 기록은 입력한 본인 화면에만 보인다. 즉 v1은 **자기 최고 기록 갱신용**이고, 사용자 간 경쟁은 v2에서 DB를 붙여야 성립한다.

이 제약을 v1에서 보완하기 위한 장치:
- 랭킹 화면에 저장 범위를 명시해 오해를 방지한다 (FR-6.10)
- 결과 화면에서 자기 최고 기록과 비교해 재도전 동기를 만든다 (FR-5.7)
- 결과 카드를 이미지·텍스트로 복사해 외부에서 수동으로 비교할 수 있게 한다 (12번 확장 아이디어)

### 12.1 서버 랭킹(v2) 도입 시 함께 정할 것
- 기록 조작 방지: 클라이언트가 점수를 그대로 전송하면 위조가 쉽다. 최소 소요 시간 하한, 제출 빈도 제한, 서버측 채점 중 어디까지 적용할지 결정 필요
- 닉네임 정책: 중복 허용 여부, 금칙어 필터, 길이 제한
- 기존 로컬 기록의 서버 이관 여부
- 랭킹 조회 범위: 전체 / 기간별(주간·월간) / 카테고리별
- **만점자 변별력**: 동점을 먼저 달성한 순으로 가르므로, 만점자가 많아지면 상위권이 초기 기록으로 고정된다. 문제 수 확대, 난이도 상향, 기간별 랭킹 분리 중 어떤 방식으로 풀지 결정 필요
- 기록 시각의 신뢰성: 로컬 시계는 조작 가능하므로 서버 타임스탬프를 기준으로 전환
