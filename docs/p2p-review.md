# P2P 검토: 서버 없이 또는 서버 장애 때 온라인 방을 돌릴 수 있나

| 항목 | 내용 |
| --- | --- |
| 작성일 | 2026-10-27 |
| 상태 | 검토 문서. 결정은 소유자가 한다 (PRD 10.2) |
| 관련 | PRD FR-7.9(온라인 전용 전환), `deploy/oracle/README.md` |

혼자 하기를 없애고 온라인만 남기면, 서버가 꺼진 동안에는 게임을 할 수 없다. 서버 대신(또는 서버가 꺼졌을 때만)
브라우저끼리 직접 잇는 P2P(WebRTC)로 돌리면 어떤지 검토한다.

## 1. 지금 서버가 맡은 일

P2P로 옮기려면 아래를 누군가의 브라우저가 대신 맡아야 한다.

| 서버의 일 | 왜 서버에 있나 |
| --- | --- |
| 정답 보관과 채점 | 정답은 공개 전까지 서버에만 있다. 브라우저가 들고 있으면 개발자 도구로 미리 볼 수 있다 |
| 비공개 문제 은행 | 온라인 은행은 공개 `data/`와 따로 쓰고 Git에도 없다 (`ONLINE_QUESTION_BANK.md`) |
| 진행 시계·마감 | 마감과 공개(8초)는 서버 시계가 정한다. 참가자 기기 시계를 믿지 않는다 |
| 로비·방 코드 | 처음 보는 사람끼리 방을 찾고 코드로 들어오는 자리다 |
| 접속 상태·방장 승계 | 끊긴 사람을 60초 뒤 빼고, 끊긴 방장의 자리를 넘긴다 |
| 요청 한도 | 한 사람·한 주소가 방을 쏟아 내거나 답을 두드리지 못하게 한다 |
| 서버 랭킹(계획) | 점수를 서버가 채점하므로 랭킹을 믿을 수 있다 (PRD FR-7.9 2단계) |

## 2. 세 가지 방식

### A. 완전 P2P — 방장 브라우저가 서버 노릇

- **그래도 서버가 필요하다.** WebRTC는 서로를 처음 찾는 signaling 서버가 있어야 연결된다. 학교·통신사의 NAT(대칭형)
  뒤에서는 직접 연결이 안 되는 경우가 흔해 중계(TURN) 서버도 필요하다. TURN은 오가는 트래픽을 그대로 중계하므로
  트래픽에 비례해 비용이 든다.
- **정답을 숨길 수 없다.** 채점하는 방장 브라우저가 정답을 들고 있다. 방장은 미리 볼 수 있고, 은행이 브라우저로
  내려가는 순간 비공개 은행이라는 전제가 사라진다.
- **방장이 나가면 판이 끝난다.** 상태를 다른 참가자에게 넘기는 일(호스트 이전)이 복잡하고, 휴대폰은 앱을 바꾸면
  연결이 곧 끊긴다.
- **랭킹을 믿을 수 없다.** 점수를 브라우저가 보고하므로 조작할 수 있다. 서버 랭킹(소유자 결정)과 맞지 않는다.
- **공개 방 목록이 없다.** 로비는 서버가 있어야 성립한다.

### B. 하이브리드 — 로비·채점은 서버, 이동·채팅만 P2P

- 서버 부하에서 가장 큰 몫인 이동·채팅 방송을 브라우저끼리 주고받아 서버 일을 줄인다.
- **장애 대비는 되지 않는다.** 서버가 꺼지면 로비도 채점도 함께 멈춘다.
- signaling·TURN과 두 갈래의 연결(서버 소켓 + P2P)을 함께 유지해야 해 복잡도가 크게 는다.
- 서버 부하가 실제로 한계에 닿을 때(부하 측정 결과로 판단) 다시 볼 만하다.

### C. 장애 때만 P2P

- 서버가 꺼졌을 때는 signaling 서버도 없다. 남는 방법은 같은 자리의 사람끼리 코드나 QR을 손으로 주고받는 수동
  연결인데, 사용성이 나쁘고 NAT 문제는 그대로다.
- 평소에는 쓰지 않는 길이라 고장 나도 모르고 지나가기 쉽다.

## 3. 비교

| | 지금(서버) | A 완전 P2P | B 하이브리드 | C 장애 때만 P2P | 비상용 연습(로컬) |
| --- | --- | --- | --- | --- | --- |
| 서버가 꺼졌을 때 | 못 함 | 못 함(signaling 필요) | 못 함 | 수동 연결이면 일부 | 혼자 연습 가능 |
| 정답 비공개 | 지킴 | 못 지킴 | 지킴 | 못 지킴 | 공개 은행이라 해당 없음 |
| 서버 랭킹 신뢰 | 지킴 | 못 지킴 | 지킴 | 기록 안 함 | 기록 안 함 |
| 추가 인프라 | 없음 | signaling + TURN | signaling + TURN | 없음(수동) | 없음 |
| 구현 크기 | — | 매우 큼 | 큼 | 큼 | 작음(지금 코드 재사용) |

## 4. 권장

1. **서버를 유지한다.** P2P는 정답 비공개와 서버 랭킹을 함께 지킬 수 없고, 서버 장애 대비 효과도 없다(A·B 모두
   signaling 서버가 필요하다).
2. **장애는 빨리 알고 빨리 되돌린다.** GitHub Actions 운영 점검(15분)과 «운영 경보» 이슈, 배포 문서의 롤백 절차로
   대응한다.
3. **서버가 닿지 않을 때만 지금의 혼자 하기를 «연습(기록 안 남음)»으로 연다.** 지금 코드를 거의 그대로 쓰고, 온라인
   전용 전환(FR-7.9 3단계) 뒤에도 서버 장애에 막다른 길이 생기지 않는다.
4. **B(하이브리드)는 부하 측정에서 이동·채팅 방송이 서버 한계를 정하는 것으로 드러날 때 다시 검토한다.**

## 5. 소유자 결정이 필요한 것

- 서버 장애 때: 비상용 연습을 남길지(권장), 안내만 띄울지
- B를 검토할 부하 기준(예: 0.5 CPU 컨테이너에서 동시 몇 명을 넘으면 검토)
